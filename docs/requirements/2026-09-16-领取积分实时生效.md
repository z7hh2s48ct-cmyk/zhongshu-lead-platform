# 领取积分实时生效

## 已确认的业务规则

管理员保存客资领取积分后，后续领取按最新配置实际扣费。该规则覆盖平台录入、飞书导入、加盟商提交和其他历史来源，以及已经派发但仍待领取的记录。例如以 100 分派发，后台改成 150 分后领取，实际扣 150 分；领取前再改成 120 分，则实际扣 120 分。

已领取的扣费记录不追补、不重算。后续退款、奖励和经营统计使用实际领取时保存的金额。重复点击或请求重试只返回原领取结果，不因配置变化二次扣分。供客奖励仍为独立设置，其领取时快照和后续结算规则不变。

本规则替代 9.12 文档中“仅运营来源使用固定领取积分”和“派发时锁定领取积分”的约定。其他 9.12、9.13、9.15 已确认规则保持原业务含义。

## 数据及事务

- 沿用 `SystemConfig(domain=lead_points,key=global)`，配置字段 `operation_claim_points` 保留以兼容已部署数据和客户端，语义扩展为所有来源领取价。不新增依赖或表结构。
- 未首次保存全局积分的环境继续采用既有规则；已经配置的环境所有来源统一读取全局价格。
- 待领取展示和预占积分读取当前配置，不通过批量改写历史派发单实现调价。
- 领取成功时，在同一事务内保存 `points_price`、`claim_points`、规则版本，扣减余额并生成流水。失败或报价不符时不产生扣费。
- 配置保存和实际领取取价必须有明确事务顺序：已提交的新配置不能被后开始的扣费忽略；领取金额确定后到提交之间保持规则一致。
- 调价后账户余额不足时拒绝领取，不沿用旧低价、不扣成负数。

## 接口约定

`GET /api/v1/v1.2/assignments`、派发详情和相关管理展示，在待领取状态返回最新 `points_price`；已领取及其他历史状态返回该记录原金额。待领取报价读取不产生流水或修改派发状态。列表一次读取配置，避免逐条查询。

`POST /api/v1/v1.2/assignments/{assignment_id}/claim` 增加可选 JSON 请求体：

```json
{"expected_points": 150}
```

`expected_points` 是严格正整数，表示用户页面已展示并确认的金额，不作为服务器定价来源。服务器对比最新价格，不一致时返回 HTTP 409 / `CLAIM_PRICE_CHANGED`，错误详情包含 `expected_points` 与 `current_points`，不扣分。页面刷新报价并提示，再由用户按新价确认领取；不自动重试扣费。

原 V1.2 无请求体客户端继续可用，扣费仍以后端当前价格为准。旧领取接口保留原 `idempotency_key` 要求并增加可选 `expected_points`。已经成功领取的幂等重放返回原金额，不重新进行报价确认。

领取成功响应中的派发金额、积分流水 `delta` 和余额应一致。前端成功提示实际扣除积分。打开旧页面后点击领取先刷新报价，正式扣费请求仍带确认金额，以覆盖页面刷新和提交间再次改价的竞争。

## 验收范围

1. 三种主要来源的新派发均按全局积分报价。
2. 旧 100 分待领取单：配置改 150 后列表、详情、预占积分同步为 150，领取流水为 -150。
3. 改价为 120 后，新领取扣 120；原已领取单及幂等重放仍为 150。
4. 页面确认价过期返回 409 且无扣费；余额不足拒绝领取。
5. 单条和批量候选余额、旧领取入口、公司与员工列表、后台详情保持一致。
6. 真实 PostgreSQL 下验证改价与领取事务顺序、重复领取和同账户并发，不只依赖 SQLite。
7. 原权限、退款金额、供客奖励快照和历史统计回归通过。

## 发布与回退

代码须先经独立评审、相关完整测试、静态与安全检查后提交推送，再使用匹配提交的已验证镜像发布。上线前备份数据库及当前版本和配置，API、Scheduler、导出 Worker 使用相同镜像，静态页面缓存版本同时更新。

领取积分改价本身没有数据库迁移或历史批量重算。本次与 9.15/9.16 反馈合并发布，整体版本包含 `0022_return_clock_pause`，上线必须暂停业务写入、备份并完成迁移与对账。退回计时迁移的升降级快照规则见同日反馈整改文档。积分改价代码可整体回退，但旧代码恢复“派发时锁价”语义；需要先暂停新领取，核对待领取单的历史价与当前配置后恢复业务。已完成的实际扣费与积分流水必须保留，不为回退覆盖生产数据库。
