# 固定积分及 9.12 反馈整改

确认范围：系统管理员配置运营客资领取积分 X、加盟商供客积分 Y，另包含全国服务区域全选、退回草稿与运营待办分离、待运营补充漏列检查、公海手机号筛选及导出。

## 实施约定

- X 为正整数，Y 为非负整数。通过现有 SystemConfig 保存版本；首次配置前沿用现有规则，管理员填写后启用固定积分，避免擅自确定实际积分金额。
- 运营来源为 PLATFORM_MANUAL、FEISHU_IMPORT。派发时锁定领取积分，之后修改配置不影响已有派发单。
- Y 在客资领取时生成供客积分记录并锁定；接收方电话确认有效后计 3 个工作日，到期无待处理退回方可入账。首次退回仍是领取后连续 48 小时。正式提交退回冻结供客积分，退回成立则取消、不成立则恢复观察。历史积分记录不重算。
- 全国全选复用现有城市编码列表与地区匹配，支持新建和编辑，保留主要城市选择；不增加地区模型或依赖。
- 待补充仍是当前未处理队列：失败保留、成功转派退出。先修复可重现的跨栏目筛选残留，再用历史未处理记录回归；不猜测生产数据、不盲目回填已完成记录。
- 公海手机号按完整号码标准化并哈希等值查询，列表、总数、导出一致；任务和审计仅持久化哈希。

## 顺序与验证

1. 先增加行为测试复现缺口；并行实现独立后端，主线程负责前端及集成。
2. 复用积分流水、结算与地区结构；删除被两个固定积分输入替代的比例编辑入口，保留旧记录原比例说明。
3. 核验权限、配置版本冲突、锁价、结算幂等、48 小时与 3 工作日、全国选择、未处理队列、筛选与导出。
4. 执行静态检查、相关完整测试、安全检查、差异审查后提交。此交付为本地分支，生产部署及历史数据实查另记证据。

## 接口与兼容约定

### 两个固定积分

仅 `SUPER_ADMIN` 可调用 `GET /api/v1/v1.2/admin/lead-points-settings` 与 `PUT /api/v1/v1.2/admin/lead-points-settings`。读取结果仍使用项目统一响应信封，`data` 包含：

| 字段 | 含义 |
| --- | --- |
| `configured` | 是否已保存固定积分 |
| `operation_claim_points` | 运营客资领取积分；未配置时为 null |
| `supplier_provision_points` | 加盟商供客积分；未配置时为 null |
| `version` | 当前配置版本；未配置时为 0 |

保存请求一次传入 `operation_claim_points`、`supplier_provision_points` 和上次读取的 `expected_version`。两个积分必须是 JSON 整数，不接受小数、布尔值或数字字符串；X 范围为 1～2147483647，Y 范围为 0～2147483647。保存成功返回同一结构与新版本，写入 `V12_LEAD_POINTS_SETTINGS_UPDATE` 审计。过期版本返回 HTTP 409、错误码 `LEAD_POINTS_SETTINGS_VERSION_CONFLICT`，客户端保留输入并提示刷新后重新核对；普通运营、加盟商无法修改。

配置保存在 `SystemConfig(domain=lead_points, key=global)`，每次保存发布一个版本并退役旧版本。PostgreSQL 通过事务锁串行化保存，SQLite 开发环境通过写锁串行化。运营来源的单条、批量和旧派发入口均复用同一次配置读取及版本，派发单保存领取积分；供客积分沿用 `SupplierLeadReward`，领取时保存固定金额与 `FIXED` 规则快照，结算按原记录执行。

### 全国区域、公海筛选与退回队列

- `POST /api/v1/companies/simple` 的 `region_codes` 和 `PUT /api/v1/v1.2/admin/companies/{company_id}/service-areas` 的 `region_codes` 上限从 100 调整为 1000。主要城市、区域权限和审批逻辑不变。
- `GET /api/v1/v1.2/public-pool/leads` 新增可选 `phone`，按完整手机号标准化后查询；空值不筛选，格式错误返回 HTTP 422 / `PHONE_INVALID`。与其他筛选条件组合后，列表总数和分页一致。
- `POST /api/v1/v1.2/reports/leads/exports` 的公海导出沿用现有请求结构，`phone` 与列表使用相同规则。任务与审计持久化 `phone_hash`，不写入明文查询号码；导出权限和下载时效不变。
- 管理人员读取 `GET /api/v1/v1.2/returns` 时，不带状态默认只返回已正式提交记录；显式 `status=DRAFT` 可查看草稿，页面只读。加盟商仍可查看和编辑自己的有效草稿。超过领取后 48 小时未提交的草稿由 Scheduler 每 5 分钟最多处理 200 条，标记 `EXPIRED` 并留下 `V12_RETURN_DRAFT_EXPIRED` 业务事件，不进入正式审核或冻结积分。
- 待补充队列继续按 `PRE_DISPATCH_REWORK_REQUIRED` 查询当前未处理记录。修复客资栏目与待补充栏目切换时残留日期、来源、手机号等筛选条件导致的漏列；同一栏目内的主动筛选仍保留。测试覆盖较早创建记录、其他待办排除、补充失败保留及成功退出。

### 上线与回退边界

无表结构变更、无批量历史数据回填、无新增依赖。管理员需要在上线后填写实际 X/Y；测试中使用的积分仅写入隔离数据库。配置变更本身可通过再次保存原数值恢复，原历史快照保留；若回退至不支持固定积分的旧代码，新业务将恢复旧价格及比例规则，因此应暂停新派发和领取，核对旧规则后按正常发布回退流程操作。

生产环境中「历史待补充记录为何缺失」仍需按具体 Lead 检查其当前状态、待办原因与操作历史；本次修复和测试不把已处理记录强行恢复为待办。
